Two audit findings that change the brief

There is no Organization entity. TaskFlow is single-tenant — one company, many departments. Adding organization_id would introduce a table with exactly one row and a foreign key on every objective that never varies. See decision D1.

Soft deletion here is is_archived BOOLEAN, not archived_at. That is the convention on tasks and notes. See decision D2.

Part A

Existing architecture map

How User → Department → Task works today, including the parts the OKR layer must not disturb.

departments (id, key, name, colour, is_active) │ ├── users.department_id → a person belongs to one department (nullable) │ │ │ └── role + extra_permissions[] − revoked_permissions[] │ = effective permissions (computed per request) │ └── tasks.department_id → NOT NULL. Sets the task reference: MKT-14 │ ├── assignee_id → accountable owner (carries the black mark) ├── follower_id → second worker, no deadline accountability ├── task_collaborators → tagged for cross-department visibility ├── parent_task_id → sub tasks; parent progress = avg(children) └── status_id → workflow_statuses.stage → drives every dashboard

Visibility

A caller with task.view.all sees everything. Otherwise a task is visible if they are the assignee, follower, reporter or creator, or it belongs to their department, or they are tagged on it. This is one SQL fragment, visibilityClause(), reused by every task query.

Editing

canEdit() grants full edit to assignee, follower, reporter, creator, or anyone with task.edit.any. A narrower path lets anyone with task.assign change only ownership on a task they can see.

Audit trail

task_activity records every field change, completion, reopen and link. Its task_id is NOT NULL with a foreign key to tasks — so it cannot hold objective or key-result events without altering an existing table. See D5.

Configuration

A settings table holds JSONB values merged over code defaults (blackmarks, workload, taskTypes, organisation). This is the natural home for OKR health thresholds and the module's on/off flag.

  owner_user_id       INTEGER NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
  start_date          DATE NOT NULL,
  end_date            DATE NOT NULL,
  priority            TEXT NOT NULL DEFAULT 'medium'
                        CHECK (priority IN ('low','medium','high','critical')),
  status              TEXT NOT NULL DEFAULT 'DRAFT'
                        CHECK (status IN ('DRAFT','ACTIVE','ON_HOLD','COMPLETED','CANCELLED')),
  manual_health       TEXT CHECK (manual_health IN
                        ('ON_TRACK','AT_RISK','OFF_TRACK','COMPLETED','NOT_STARTED')),
  health_override_reason TEXT,

Progress engine — the two numbers

Result and execution progress answer different questions and are computed from different sources. They are never conflated, and completing tasks never moves the result number. 

// RESULT PROGRESS — did the outcome actually happen?
INCREASE:  (current − baseline) / (target − baseline)
DECREASE:  (baseline − current) / (baseline − target)
BINARY:    current >= 1 ? 100% : 0%
TASK_ROLLUP: falls back to execution progress (this is the one type where
             the outcome IS the work being done)

// guards: denominator 0 → null (shown as "not measurable", not 0%)
//         target null   → null
//         clamp 0–100 for display; raw value kept for over-achievement

// EXECUTION PROGRESS — how much of the linked work is finished?
   count(linked tasks where stage = 'done') / count(linked tasks)
   // weighted by contribution_weight when present; null when no tasks linked

// OBJECTIVE PROGRESS — weighted roll-up of its key results
   Σ(KR result progress × KR weight) / Σ(KR weight)
   // KRs with null progress are excluded from both sums, not counted as 0

Health engine

Thresholds live in settings.okr.health, editable without a deploy, defaulting to the values in the brief.

time_elapsed = (today − start_date) / (end_date − start_date)

COMPLETED    progress = 100
NOT_STARTED  today < start_date
ON_TRACK     progress >= time_elapsed − 10pp
AT_RISK      progress >= time_elapsed − 25pp
OFF_TRACK    otherwise, OR end_date passed and progress < 100

// auto_health is always computed and stored alongside any manual override,
// so the UI can show "Manually set to ON_TRACK — system says AT_RISK".

Feature flag

No flag framework exists and the brief says not to build one. The settings table already stores JSONB config merged over code defaults — so the flag is one key, settings.okr.enabled, default false. The router mounts unconditionally but returns 404 while disabled; the nav entry and the task-dialog section are hidden from the settings payload the client already fetches. Turning it on is a settings change, not a deploy.

Sign-off required

Six decisions

Each of these is a place where the brief and the existing codebase disagree, or where storing a value risks a second source of truth. I have a recommendation for each; I will follow your call.

D1 · organization_id

Do not add an Organization entity

The brief says "if the current architecture supports organizations" — it does not. TaskFlow is single-tenant. Recommendation: omit organization_id. scope_type = 'COMPANY' already expresses company-wide. If multi-tenancy ever arrives it belongs on departments and users first, as its own project.

D2 · soft deletion

Use is_archived, not archived_at

The brief suggests archived_at; the codebase uses is_archived BOOLEAN on tasks and notes. Recommendation: match the existing convention so one archive idiom covers the whole app.

D3 · stored vs derived progress

Derive progress and health; do not store them

The brief lists progress_percent and auto_health_status as columns. Storing them creates a second source of truth that silently goes stale whenever a task is completed, a check-in lands, or midnight passes. Recommendation: compute both in SQL on read — the inputs (current_value, weights, task links, dates) are all stored, so the numbers are always right. At your data volumes this costs nothing. If a dashboard ever gets slow, the fix is a materialised view, which we can add without changing the API.

D4 · objective on task

No objective_id on tasks — confirmed

Following your rule exactly: the objective is reached via task → link → key_result → objective. The task dialog shows it read-only, derived from the chosen key result. No change to the tasks table at all.

D5 · audit trail

New okr_activity table rather than widening task_activity

task_activity.task_id is NOT NULL with a foreign key to tasks. Reusing it would mean making that column nullable — an existing-behaviour modification to a table with live data, which the brief forbids. Recommendation: a parallel table with the same shape, so the pattern is familiar and the existing audit trail is untouched.

D6 · scope of phase 2

Ship the core before the extras

The full brief is large. Recommendation: build objectives, key results, check-ins, task linking, the health engine, the goals dashboard and the task-dialog integration first — that is a complete, usable OKR loop. Then, as a second pass: contributors, cascading parent objectives beyond one level, department-page embedding, and the milestone measurement type. Say if you would rather have all of it in one delivery.

Nothing in this plan has been implemented. On approval — including your answers to D1–D6 — the work lands as one migration, five new server files, five new client files, nine additive edits, and a new test file, behind settings.okr.enabled.
